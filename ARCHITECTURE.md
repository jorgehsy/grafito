# Architecture

Grafito listens to a talk and draws it live. Claude never draws anything itself: it emits **ops** (small, coordinate-free changes to the board), and the browser lays out and animates the result. Terms in bold are defined in [`GLOSSARY.md`](GLOSSARY.md); decisions are in [`docs/adr/`](docs/adr/).

Some file and identifier names are still Spanish. They are being renamed to the glossary terms.

## Package map

```
apps/
  web/        Vite + React: rendering engine, live session UI, speech, demos
  server/     Express + Anthropic: POST /api/board, saved sessions, eval script
packages/
  contract/   the browser/server contract: ops, tool definitions, op validation, pricing
  board/      the board engine, no DOM: model, layout, routing, render tree, animation queue
  icons/      icon catalogs: AWS curated list, SVGs, NOTICE, fetch script
  wellarchitected/  the Well-Architected digest (CC BY-SA 4.0): pillars, principles, question and best-practice titles, fetch script
  config/     shared tsconfig bases and ESLint flat config
```

Dependencies point one way: `apps/*` → `packages/*`. `board` depends on `contract` and `icons`; `contract` depends on `icons`; `wellarchitected` depends on nothing and only `apps/server` uses it. `packages/*` never import from `apps/*` and use no DOM or Node APIs (see [ADR 0001](docs/adr/0001-turborepo-monorepo-deep-modules.md)).

## Pipeline

speech (or a sketch) → fragment → `POST /api/board` → Claude tool calls → ops → board model → layout → render tree → animated SVG

1. **Speech.** `apps/web/src/live/speech/webSpeech.ts` wraps the browser's speech recognition behind the `SpeechSource` interface (`speech/types.ts`). Interim results show as subtitles; `live/ui/useMic.ts` hands each finished result to the **live session** (`live/session.ts`, `onFinalText`), which adds it to the **transcript** and groups it with `speech/grouper.ts` (short pause or length limit; longer while the wake word is present). Typed text enters the same way.
2. **Fragment.** The session turns each grouped text into a fragment. `live/instruction.ts` splits it at the **wake word** into content and an **instruction**. `live/scheduler.ts` keeps one request in flight and joins the content that arrives meanwhile into one **batch**; each instruction goes alone.
3. **`POST /api/board`.** `live/sse.ts` posts the batch with the **board text** (`packages/board/src/serialize.ts`), the **summary**, the Claude model, the **shape preference**, the **mode**, the enabled **icon catalogs** and the **language** (`lang`). In development Vite proxies `/api` to the server on port 8787.
4. **Claude tool calls.** `apps/server/src/routes/board.ts` validates the request, builds the system prompt (`systemPrompt`, `prompt/system.ts`: English, ending with a line that names the language Claude writes the board in; that line is a separate block outside the cached prefix) and the user text (`buildUserText`, `prompt/user-text.ts`), and streams from the `ClaudeClient` of the model's provider (`claude/client.ts`; `index.ts` builds them with `buildClients`, tests pass the fake; see ADR 0004). The Anthropic adapter (`claude/anthropic.ts`) sends the tools for the enabled catalogs (`toolDefs` in `packages/contract/src/parse.ts`). `claude/stream.ts` retries once, only if no op has been sent yet.
5. **Ops.** `claude/stream.ts` buffers each `tool_use` block's JSON and parses it with `parseOp` when the block ends; the route sends it to the browser as an SSE `op` event. Invalid ops are sent as warnings and skipped. `usage`, `done` and `error` events carry cost, timings and failures.
6. **Board model.** `live/sse.ts` parses the stream, runs `parseOp` again on each op (anything that fails becomes a warning), and the session submits each op to `BoardController` (`packages/board/src/controller.ts`), which applies ops one at a time with `applyOp` (`model.ts`). `applyOp` checks only what needs the board (ids, zone kinds); the shape is `parseOp`'s job. The board holds no coordinates.
7. **Layout.** `computeLayout` (`layout/index.ts`, one file per zone kind next to it) positions everything per zone kind: ELK for flow, system and data (a system zone with groups is one compound ELK run, `INCLUDE_CHILDREN`, so each group's box comes from its children; see the notes in `layout/elk.ts`), d3-hierarchy for mindmap, stacked rows for list and compare, custom code for scale, cycle, timeline and tree. `route.ts` routes connections between zones around obstacles. To add a zone kind, follow `docs/adding-a-zone-kind.md`.
8. **Render tree.** `buildTree` (`tree.ts`) turns board + layout into a flat list of **render items** with stable keys. `diffTrees` (`animator.ts`) compares it with the previous tree, and the **animation queue** plays the result: draw, update, ink (pencil to ink) and remove in order, moves in parallel, faster when work piles up.
9. **Animated SVG.** `apps/web/src/render/engine.ts` implements the queue's `Sink`: it builds each **visual** with rough.js (`render/visuals.ts`), animates strokes, fills and text, adds the **service stamp** (`render/stamp.ts`) and moves the camera (`packages/board/src/camera.ts`).

### Side paths

- **Session records.** The record format and `parseRecord` live in `packages/contract/src/record.ts`: version 3, a union on `appMode` (`"live"` or `"architect"`). A version 2 file has no `appMode` and is read as a live record (converted in memory, written back as version 3 on the next save); version 1 is rejected. Each session builds its record with `snapshot()` and autosaves it to the browser, in its mode's own slot (`RECORD_KEYS` in `storage.ts`), and to `POST /api/sessions`; `apps/server/src/sessions.ts` parses it and writes it under `apps/server/sessions/` (one folder, the same file naming for both modes; the list shows each file's `appMode`). Records can also be exported, imported and restored in the browser (`restore(record)`); a record always reopens in its own mode, and importing one switches the app to it (`BoardApp` hands an architect record to the architect panel). Restoring parses every recorded op with `parseOp` (all catalogs on) and drops the invalid ones with a warning. The exported SVG comes from the render engine (`Engine.exportSvg()`).
- **Architect records.** The body is a `timeline` of `turn` entries (typed text, ops as received with `say`, usage, cost, timings, `promptVersion` = `ARCHITECT_PROMPT_VERSION`, `error?`) and `click` entries (`accept`/`reject`, proposal, time), in the order they happened, plus the summary; no transcript or shape, and `medianVoiceFirstMs` is null. A turn's `actions` are not stored: they are the clicks between it and the turn before. Restore replays: `replayArchitect` (`packages/board`, shared with the eval) makes the system zone, applies each turn's drawing ops (a broken turn with what it got) and each click as the same `accept`/`reject`, and returns the board, the ops for `BoardController`, the parsed turns and the clicks after the last turn, which the session queues again as the next `actions`. Bubble markers, the open bubble, `recent` and `PROPOSALS` are rebuilt from that, never stored; open proposals come back in pencil. There is no undo in architect mode (`undone` is live-only). The architect panel autosaves when it unmounts too (`close()`), and offers an unclosed architect session in its own restore banner.
- **Architect mode** (the toolbar's third mode button, or `?mode=architect`). `BoardApp` mounts `architect/ui/ArchitectPanel.tsx`, whose architect session (`architect/session.ts`) wipes the board and makes the one system zone (`architectZoneOp`, id `ARCHITECT_ZONE_ID`); Claude never creates zones there. Leaving the mode wipes the board without asking. Each message typed in the one text box is a **turn**: the session posts it to `POST /api/architect` (`routes/architect.ts`) with the board text, the summary, the last 3 turns word for word (`recent`: user text and bubble text), the model, language and catalogs. The route streams like `/api/board` (same SSE events, adapters and retry rule) with the architect prompt (`prompt/architect.ts`: persona rules and the **Well-Architected digest** from `packages/wellarchitected`, cached with the tools, then the same language line as live mode outside the cache) and the `architect` op set: the kept board ops (`add_component`, `connect`, `update_label`, `delete`, `set_service`, `update_summary`) plus `say`, the speech bubble, and the group ops ([ADR 0005](docs/adr/0005-nested-aws-groups.md)): `add_group`, `set_parent` and `add_component`'s `parent`. Groups live in the model as a tree inside the system zone, show in the board text as a `GROUPS` tree, and render as AWS-style boxes (`GROUP_STYLES` in `palette.ts`) in their own layer under everything else. `ClaudeParams.opSet` picks the tools each adapter sends and the set `parseOp` accepts. Architect turns default to Sonnet (`ARCHITECT_DEFAULT_MODEL`), effort medium, 16000 max tokens, and keep adaptive thinking (`adaptiveThinking`; the subscription adapter disables thinking only for live turns). In the browser, drawing ops go to `BoardController`, applied with `applyArchitectOp` (as the replay does), so a `delete` of the system zone is refused with a warning; the turn's last `say` is the speech bubble, kept by the session and never put on the board.
- **Proposals** (architect mode). `propose {id, label, alternative_to?}` opens a proposal; `add_component`, `add_group` and `connect` may carry `proposal`, and what they draw is pencil (without it, ink). Proposals only add: no change or delete op takes one. The board model keeps the open proposals (`Board.proposals`) and tags each pencil item with its id; `accept` turns them to ink and erases the other of two alternatives (`alternativesOf`), `reject` erases what was drawn under it (ink inside an erased group moves up a level, arrows touching it go). Both are plain `applyOp` ops, so a click can apply them locally the same way. A drawing op under a proposal that is not open is not drawn (warning): ink means the user agreed, so it is never the fallback. The board text tags pencil items `[pencil P3]` and lists the open ones under `PROPOSALS` (two alternatives as A and B). Layout keeps two alternatives next to each other (`alternativesTogether` in `layout/zones.ts`). The render item carries `data.pencil` outside `sig`: `visuals.ts` draws it grey, thin, sketchy and see-through, a pencil-to-ink change is an `ink` task (the engine draws the ink over the pencil, then fades the pencil out), and an erased proposal leaves with the usual delete fade. The user's yes/no/A/B is typed text sent to Claude, which answers with `accept` or `reject`.
- **Speech bubbles and bubble markers** (architect mode). `architect/bubbles.ts` holds the pure parts. `bubbleMarkers` makes one marker per turn from its `say` ops alone (last one wins; a turn with none is a muted marker), so a replayed session rebuilds the same rail. `BubbleView` (`current`, `showPast`, `toggled`; not saved) says which bubbles are open: the latest turn's, past ones reopened from their marker, or all of them after a click on the rail; a new turn shrinks reopened ones back. `resolveTarget` turns `say.target` into render keys: a component, group or arrow, or the items of an open proposal; anything else is a general bubble. `SpeechBubbles` re-places every open bubble each frame from `Engine.screenRect` (a proposal uses the box around its items): `placeBubble` tries spots beside the target, on screen, scoring overlap with the target and with the ✓/✗ toolbar, rail, text box, side toolbar, brand and the bubbles placed before it, then with other components; `tailTip` and `tailShape` draw the tail (to the nearest side of an item, or toward a proposal's middle). A target off screen gives a general bubble. `TimelineRail` draws the markers as buttons with en/es labels; the tooltip shows on hover and keyboard focus.
- **Clicks on proposals** (architect mode). Every visual group the engine draws carries `data-key` (its render item key) and, while pencil, `data-pencil`; pencil elements and groups get a transparent clickable area and pencil arrows a wide transparent stroke (`data-hit`, left out of the exported SVG). A press that moves less than 5px is a click, not a pan: `Engine.onPick` gets the pencil key under it, or null for ink and paper. The architect panel resolves it with `pickProposal` (`proposalOf` in the model): one of two alternatives is chosen at once (an `accept`, the other erased); any other proposal is selected (`Engine.select` outlines its items, `proposalItems`) and `ProposalToolbar` shows ✓/✗ by the clicked item, placed each frame from `Engine.screenRect` so it follows pans, zooms and layout moves. Escape or a click elsewhere deselects. ✓/✗ call `session.decide`, which submits `accept`/`reject` through the same `BoardController` path as Claude's ops, with no Claude call, and queues the click (`{type, proposal, at}`); a click on a proposal that is closed, or already settled by a queued click, is ignored. While a turn is in flight there are no clicks: the session refuses them, the toolbar's buttons are disabled with a hint to wait, and an alternative is selected instead of chosen, because the replay applies a click only between turns. A turn sends the board only once every pending submit (clicks, the last turn's ops) is applied. The next turn sends the queue as `actions` (always present, `[]` when empty) and clears it; a click alone is never a turn. The route validates `actions` with `parseClicks` and the user text lists them under `USER CLICKS SINCE LAST TURN`; the prompt says they are already applied, not to re-send them, and to acknowledge them briefly.
- **Architect mode: sketch turns, the data zone and the review.** Three additions to the architect op set (`ARCHITECT_PROMPT_VERSION` 6), all in `packages/contract/src/ops.ts`. *Sketch turns*: `LivePanel` mounts the same draw dock and `useSketch` in architect mode with the architect session as its `sendSketch`; `session.sendSketch` waits for the turn in flight, then posts `sketch: { hints, image? }` with the turn to `POST /api/architect`, which adds `ARCHITECT_SKETCH_RULES` as a system block after the cached prefix, the strokes under `USER SKETCH` in the user text and the picture as an image block. The strokes are removed when the turn changed the board (`drawsOnBoard`); the turn is recorded with `sketch` (the strokes in text) and an empty `text`. *Data zone*: the architect set has `add_entity`, `set_fields` and `relate`, always ink. The app, not Claude, makes the data zone (`ARCHITECT_DATA_ZONE_ID`, `architectDataZoneOp`, placed below the system zone) just before the first entity: the session in the browser, `replayArchitect` on restore; it is never in the record, and `applyArchitectOp` refuses to delete it. *Review*: `assess_pillar {pillar, status, note}`, `add_finding {id, pillar, severity, text, target?, best_practice?}` and `resolve_finding {id}` draw nothing. `packages/board/src/review.ts` folds them into a `Review` (`applyReviewOp`, `reviewOf`, `serializeReview`); the session keeps it in its state, sends it as `review` text (`REVIEW SO FAR`) and `replayArchitect` returns it, so the record stores only the ops. `parseOp` checks the shape of a best-practice id; `routes/architect.ts` (`knownPracticesOnly`) drops one that is not in the digest from its finding, with a warning. `architect/ui/ReviewPanel.tsx` shows the pillars and the open findings, `FindingPins.tsx` puts a numbered pin on each finding's item (placed every frame from `Engine.screenRect`), and a selected finding outlines its item with `Engine.select`; the panel reserves its room through `--free-r` (`architect/architect.css`).
- **Sketch** ([ADR 0007](docs/adr/0007-sketch-beside-the-board.md)). The draw dock (`sketch/DrawDock.tsx`) sets the engine's tool: pen, eraser or hand. Strokes are kept in board coordinates in a `SketchStore` (`sketch/store.ts`), beside the board, and the engine draws them in a layer of its own on top; the camera's bounds include them. `sketch/useSketch.ts` hands in the strokes not yet handed in (about two seconds after the last one with auto on, or on ✨ / Enter): `describeSketch` (`packages/board/src/sketch.ts`) writes each stroke's shape and what it touches, with board ids, and `Engine.exportPng` renders that part of the board with the ink as a PNG. `session.sendSketch` posts both to `POST /api/board` with `mode: "sketch"`; the route adds the sketch rules (`prompt/sketch.ts`) as a system block after the cached prefix and sends the picture as an image block (the subscription adapter sends the text only). Claude answers with ordinary ops. If it drew anything, the session removes those strokes (they fade out); if not, they stay as ink and are not sent again. The record keeps the stroke description as the request's batch, not the picture.
- **Rooms** ([ADR 0008](docs/adr/0008-rooms-server-keeps-the-log.md)). `?room=<id>` puts the app in a room, always in live mode. `room/client.ts` holds one WebSocket to `/api/rooms/<id>/ws` (Vite proxies it), reconnects, and keeps the participants, cursors, Claude's status, the feed and the room's sketch (a `SketchStore` backed by the room). `room/session.ts` gives the panel the same `LiveSession` interface as working alone: speech grouping and the wake-word split stay in the browser, then each fragment goes to the room; `op` events are parsed with `parseOp` (op set `room`) and submitted to `BoardController` in order; `request` and `request_end` events become the stats rows. On the server, `Room` (`rooms/room.ts`, no sockets in it) keeps the event log, the room's board (`applyOp`), the strokes and Claude's queue: one request in flight, content fragments joined into one batch with each speaker's name, an instruction or a sketch alone. It builds the request with `boardTurnParams` plus the room rules (`prompt/room.ts`), logs each op as it streams, logs `say` without applying it, and after a sketch that drew something logs an `erase` of its strokes. Cursors and strokes in progress are passed on and never logged. `RoomRegistry` saves each room's log to `apps/server/rooms/<id>.json` and loads it back by replaying. "Collaborate" (`room/ui/PresenceBar.tsx`) posts the current board's ops to `POST /api/rooms` and opens the new room's link. A room has no undo, import or autosaved session record; export builds a live record from the log.
- **Rooms from outside: invite token, share mode, limits** ([ADR 0009](docs/adr/0009-rooms-over-a-tunnel.md)). A room is made with an invite token (`secret.ts`: `newSecret`, compared with `safeEqual`). The room link is `?room=<id>#k=<token>` (`room/start.ts`); the browser offers the token as a WebSocket subprotocol (`grafito.room.v1`, `k.<token>`), and `attachRoomSockets` closes a wrong token or an unknown room with 4403 before sending anything, and a full room with 4409 (`ROOM_CLOSE` in the contract; the client stops retrying on both). `rooms/limits.ts` holds every ceiling and its environment variable: per connection (frame size, token buckets for messages, bytes and messages for Claude, in `connect`), per room (people, strokes, Claude's queue, requests per minute, and the room cap in requests and USD, checked in `Room.refusal` before a message is logged) and per server (rooms in memory, idle expiry, in `RoomRegistry`). A refusal is an `error` message with a `code` the browser translates. `pnpm share` (`scripts/share.mjs`) builds the front, opens a Cloudflare quick tunnel and starts the server with `GRAFITO_SHARE=1`: it then listens on 127.0.0.1 only, serves `apps/web/dist` itself (`static.ts`), and mounts the guards of `share.ts` in front of every route. A guest gets the page, `GET /api/health`, `GET /api/share` and a room they hold the token of; everything else needs the owner cookie and a request made on this machine (`isLocalRequest`: loopback socket, local `Host`, no forwarding headers). The cookie is set by the one-time owner link the server prints (`/api/owner?k=<secret>`) and holds a second secret, never printed. The script starts the server first, checks it is the one answering on the port, and only then opens the tunnel and tells the server its address (`PUT /api/share/public-url`). The server assigns participant ids (`Room.identify`): `hello` carries a resume secret that the tab keeps in `sessionStorage` (`room/keep.ts`, with the invite token, which `takeRoomKey` moves off the address bar) and presents as a third subprotocol to come back as the same participant. Rate limits have three layers (connection, client address from `Cf-Connecting-Ip`, room), `sender` bounds what waits on a slow connection, an erase is broadcast but not kept and takes its strokes out of the log, and a request cut by a reset is still billed to the room cap. Outside share mode the guards do nothing and the dev flow is the same.
- **Hi-fi export.** `apps/web/src/render/hifi/` draws the render tree a second way, for documents: `svg.ts` (`renderHifi`, pure, no DOM: render tree in, SVG text out; `text.ts` estimates text widths for a system sans and shrinks a label until it fits its box; `theme.ts` holds the light and dark colours), `index.ts` (`hifiFromBoard`: `buildTree` + the catalog icons inlined + the title block from the summary; `hifiPng`: a 2x PNG made from that SVG in the browser) and `save.ts` (the downloads). It reads the same layout as the engine, so positions match the board; nothing of it goes through rough.js. Export (`exportAll` in `LivePanel.tsx`) takes the board and layout from `BoardController` and saves `<id>.hifi.svg` and `<id>.hifi.png` next to the record and the sketchy SVG. Open proposals are drawn dashed with a legend (`proposals: "exclude"` leaves them out). A render item kind or variant it does not know is drawn as a plain box with its lines.
- **Demos.** In demo mode, `Player` (`packages/board/src/player.ts`) plays a demo from `apps/web/src/demos/*` through the same `BoardController`, without the server. `demo-timeline.ts` says what a demo looks like at any moment (subtitle, chunks on the board, hand-drawn strokes, chapter), so a **seek** is `stateAt(t)` plus `BoardController.jump`, which rebuilds that board and shows it with no animation. `replay.ts` turns a session record into a demo (a **replay**). The player UI is `apps/web/src/script/*`.
- **Icons.** `packages/icons` holds the AWS SVGs; `apps/web/src/icons/aws/index.ts` loads them with Vite's `import.meta.glob` through the `@aws-svg` alias. `pnpm --filter @grafito/icons icons:aws <zip>` refreshes them from AWS's official icon package.
- **Well-Architected digest.** `pnpm --filter @grafito/wellarchitected wa:fetch` rebuilds `src/framework.generated.ts` from the live framework, by hand; see the package's `NOTICE.md`. The package is CC BY-SA 4.0, not MIT.
- **Eval.** `pnpm --filter @grafito/server eval instruction <record.json> "<instruction>"` (`apps/server/scripts/eval.ts`) replays a saved session record and runs an instruction against it, to compare prompt changes. `eval baseline <dir>` runs the two baseline instructions against every record in a folder and prints invalid ops, missing labels, zones and cost per run; `eval convert-v1` turns version 1 records into current live records. These commands take live records (version 2 or 3) and refuse an architect record. `eval architect <scenario.json | dir>... [--dry] [--runs N] [--out <dir>]` runs architect scenarios (`apps/server/scripts/architect/scenarios/`, GLOSSARY *Architect scenario*): a JSON list of steps, or `{ name?, lang?, catalogs?, start?, steps }` (default English, AWS icons on). `start` is a scripted first turn (`{ say, ops }`), never sent to Claude and recorded with model `scripted`: it sets up the board a step needs, so that step does not depend on what earlier real turns happened to draw. A step is `{ "say": "..." }`, optionally with `expect` hints (`ink`, `pencil`, `bubbleOnly`, `asksKeep`, `review`) and, with `ink`, `asked` (the services the user names, one per component), or a click by meaning (`{ "accept": "all" | "newest" }`, `{ "reject": "all" | "newest" }`, `{ "choose": 1 | 2 }`), resolved to Claude's proposal ids on the board at run time. Each say is one turn through the real architect handler, served in process (the fake adapter drives the same path in tests); the board between turns is `replayArchitect` over the timeline so far, and the request is built as the browser builds it. The checks (`scripts/architect/checks.ts`) are code rules, no LLM judge: every turn has exactly one `say`, at most one `?` in it, at most two alternatives open, only best-practice ids that exist in the Well-Architected digest, and no ink `connect` to a pencil item (the board model draws such an arrow in pencil under that item's proposal, so the check reads the ops); `expect` adds ink (something drawn without a proposal, and each `asked` service on an ink component; Claude's own additions may sit beside it in pencil, as prompt rule 11 says), pencil (drawn, all proposals), bubbleOnly (only `say` and `update_summary`), asksKeep (with 3+ pending before the turn, two alternatives counting as one, the bubble mentions keeping them, en/es word match; n/a with fewer) and review (the bubble cites a best-practice id). It runs each scenario 3 times unless `--runs` says otherwise, prints one row per step and run with pass/fail per check and cost, then each step's pass rate; a step passes when it passes in most of its runs (one answer from a model is one sample), and the command exits non-zero when a step fails, and saves each run as a version 3 architect record in `apps/server/sessions/` (or `--out`), which the app imports. The model defaults to `ARCHITECT_DEFAULT_MODEL`; plan models work. CI never calls Claude: full runs are manual, before an architect prompt change ships.
